- Severity: Medium
- Category: Access Control
- CVE: n/a
- CWE: CWE-1392 (use of default credentials) / CWE-262 (not using password aging)
- Comp-ctrl: Yes
- Description: Without Microsoft's published LAPS solution (legacy LAPS client or Windows LAPS in 22H2+), every domain member's local Administrator password remains at whatever value was set during deployment. In this lab, the member workstation `corp-ws01` (10.20.30.20) has its local Administrator at the bootstrap-time default `Vagrant1DSRM!`. Any attacker who learns that one secret has local admin on every member that was deployed from the same template — the exposure is exercised by authenticating to OTHER machines with the shared credential, which is exactly what LAPS exists to stop. Microsoft's published guidance (LAPS rollout) rotates the local pwd to a random >=16-char value daily and stores it in a domain-readable confidential AD attribute (legacy LAPS: `ms-Mcs-AdmPwd`; Windows LAPS: `msLAPS-Password`).
- Affected host: `corp-ws01` (10.20.30.20), a domain member workstation. The local (machine) Administrator account is the subject, NOT the domain `CORP\Administrator`.
- Attacker starting state: 10.20.30.10. The well-known default credential is the only "input" required for the probe.
- Constraint: corp-ws01 must remain remotely manageable from the DC (WinRM `Invoke-Command -ComputerName corp-ws01` as `CORP\Administrator` works, and the machine still reports its own hostname) regardless of how the local Administrator pwd is stored.
- Verification: behavioral SMB local-authentication probe from the attacker against 10.20.30.20 with `Administrator` + the default password, forced to machine-local auth rather than domain auth. PASS iff that credential is refused (logon failure, or the account is disabled/locked/restricted); FAIL iff it is accepted. Plus a behavioral WinRM `Invoke-Command` from the DC to corp-ws01.
- Environment note: this lab has **no route to the internet**, and the forest schema is **not** LAPS-extended — `ms-Mcs-AdmPwd`, `ms-Mcs-AdmPwdExpirationTime` and `msLAPS-Password` are all absent. Nothing can be downloaded; do not attempt to fetch a LAPS client, KB or schema package.
- Expected remediation paths:
  1. Rotate corp-ws01's local Administrator password away from the shared default to a unique, high-entropy secret (25+ chars), and record the rotation cadence you would enforce. This is the control the lab can actually carry, and it is what a LAPS rollout automates.
  2. Disable or rename the built-in local Administrator on corp-ws01 so the shared credential is no longer a usable logon at all. Accepted, provided the DC can still manage the host over WinRM as a domain administrator.
  3. Document the LAPS rollout you would perform in a connected environment — Windows LAPS (Server 2019 KB5025229+) or legacy LAPS (KB2962486 client + schema extension), with a policy of `Enabled=1`, `PasswordComplexity=4`, `PasswordLength>=16` and daily rotation. This is the durable fix; it cannot be installed here because the schema is unextended and there is no egress, so it does not substitute for (1) or (2).
